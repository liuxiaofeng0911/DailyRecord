## 1. 一句话定位

一个部署在自家服务器上的私有"每日记录"服务：每天至少一张照片 + 一段记忆点，支持账号注册登录与数据隔离，按周/月/年回看，数据完全自持；AI 描述与总结作为可插拔能力后接入。

## 2. 要解决的问题

- 文字日记回看时记忆模糊，缺少可视化锚点。
- 时间在不知不觉中溜走，需要一个低摩擦的每日签到动作。
- 现有云相册只解决"存照片"，不解决"当天发生了什么、我当时怎么想"。
- 商业日记应用存在订阅、隐私和导出锁定问题。

## 3. 核心体验

1. **今天**：登录后打开即写，上传一张或多张照片/视频，写一句记忆点，选情绪和标签，10 秒内完成；保存后其他页面立即拿到最新数据。
2. **回看**：日历热力图一眼看到记录密度，点任意一天回到当天照片与文字；支持按周、月、自定义区间、标签、情绪筛选，并可用折线/柱状/环形图观察趋势。
3. **可追溯**：每次新增、修改、删除都会留下"谁在什么时候改了什么"，照片删除可在 30 天内恢复。
4. **账户**：注册、登录、改密、退出全部设备；注册后自动获得独立照片库，自己的照片与记录彼此不可见。
5. **可选 AI**：接入本地模型后，自动为照片写一句描述，并按周/月/年汇总回顾；未接入时其余功能不受影响。

## 5. 方案总览

```
                    自有域名 + HTTPS
                          │
                Cloudflare Tunnel（可选）
                          │
                       nginx
            ┌─────────────┴──────────────┐
            │                            │
   每日记录 Vue3 + antdv-next        Immich（每账号独立用户，仅内网）
            │                            │
   记录 API (FastAPI) + 审计/回收站    照片/视频存储 + CLIP
            │
      ┌─────┴──────────┬───────────────┐
      │                │               │
 PostgreSQL        AI Worker（可选）   Session/JWT
 (系统表+记录表+审计表)   │
                    Ollama（VLM + LLM）
```

- 照片原文件只存一份，由 Immich 管理；日记库只保存 `immich_asset_id`。Immich 管理面不对公网暴露。
- 系统基础表沿用 BigTrans 的 `com_userlist`、`t_um_*`、`cod_general_codes`、`t_switch`。
- 账号认证采用 JWT + 服务端会话登记，密码 RSA 传输加密、Argon2id 落库。
- AI 是独立进程与独立开关，未部署时不影响记录、上传、统计与浏览。

## 6. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 仓库 | 单仓库 monorepo | 单人开发、前后端同步改动、接口与部署同版本管理 |
| 后端 | Python 3.12 + FastAPI | AI 生态最顺；用相同表结构/响应/认证语义兼容 BigTrans，不引入 ctos3 私有框架 |
| 数据库 | PostgreSQL 16 | 与 Immich 共用实例、独立 database；沿用 BigTrans 表名与公共字段 |
| 密码传输 | RSA-2048 公钥加密 | 与 BigTrans 前端 `crypto.js` 的登录链路一致 |
| 密码存储 | Argon2id | 比 BigTrans 的 SHA-256 更抗爆破；明确升级点 |
| 认证 | JWT + 服务端会话登记 | 与 BigTrans 的 `Authorization` 原文、响应头续签一致，同时支持撤销 |
| 照片底座 | Immich（每账号独立用户/API Key） | 上传、EXIF、缩略图、视频转码、人脸/地点、CLIP 语义搜索；账号间照片库隔离 |
| 前端 | Vue 3.5 + Vite 5.4 + antdv-next + Vuex + Less | Node 固定 18.20；借鉴 zymonitor-web 的布局、登录页、主题、请求封装与系统管理页 |
| 图表 | ECharts 6 + vue-echarts（按需引入） | 热力图、柱状、折线、环形统一实现；支持数字标签与无障碍描述 |
| 图标 | @iconify/vue + 离线 Lucide 图标集 | 线性图标风格统一；按关键词/字典自动匹配，可按标签覆盖 |
| 本地 AI | Ollama：`qwen2.5vl:7b` + `qwen2.5:7b` | 可选阶段使用，模型可替换 |
| 反向代理 | nginx | 静态资源、API 转发、缓存、限流 |
| 内网穿透 | cloudflared + 自有域名 | 免公网 IP、自动 HTTPS；宿主机端口不直接暴露公网 |
| 部署 | Docker Compose | 一条命令起停，升级可回滚 |

运行环境：后端 Python 3.12；前端 Node 18.20 + Vite 5.4。BigTrans 的 Vite 7 / Node 22 依赖不照搬，只复用其源码组织与组件写法。

端口约定：前端 nginx **9110**（宿主仅绑定 `127.0.0.1`，不对局域网/公网监听），后端 FastAPI **9111**（仅 Docker 内网）；宿主机 `cloudflared.exe` 出站长连接回源 `http://127.0.0.1:9110`，公网 HTTPS 只经 Cloudflare Tunnel，不开放路由器端口映射。

部署方式：前后端均打 Docker 镜像，`docker-compose.yml` 编排 `postgres`、`redis`、`api`、`web`；`sh scripts/build.sh --check` 一键构建启动，`sh scripts/update.sh` 完成换包更新。

Java 作为备选：若决定直接复用 BigTrans 的 Java 基础模块，则为 Spring Boot 2.6 + JDK 11 + ctos3；当前方案通过"同表结构 + 同接口语义"保留迁移空间，避免绑定私有依赖。

## 7. 关键设计决策

1. **借鉴 BigTrans，不照搬技术栈**：沿用系统表名/字段、`{code,message,data}`、JWT 原文请求头、RSA 登录、Vue 3 + antdv-next 界面；不引入 ctos3、BeetlSQL、Flink 等与本项目无关的重型依赖。
2. **单仓库**：`backend/`、`frontend/`、`deploy/`、`docs/` 同仓，接口变更与前端适配一次提交完成。
3. **时间统一东八区**：数据库 `timestamp` 存上海本地时间，接口输出 `yyyy-MM-dd HH:mm:ss`，容器与数据库会话均设 `Asia/Shanghai`。
4. **账号与数据隔离是 MVP**：注册、登录、JWT 续签、会话撤销、按用户隔离数据第一版完成。
5. **密码双阶段保护**：传输阶段 RSA 加密；存储阶段 Argon2id。去掉 BigTrans 的三次 Base64 混淆，它不提供安全价值。
6. **不重复造照片管理**：照片存储、缩略图、视频转码、人脸与语义检索复用 Immich。
7. **双库同实例**：Immich 与日记共用 PostgreSQL 实例，独立 database 与账号，省资源且隔离故障。
8. **AI 后置且可降级**：MVP 只预留字段与开关，不实现推理；未接入时记录、上传、统计、浏览全部正常。
9. **数据同步以服务端为准**：保存成功返回新 `version`，前端递增全局数据版本；页面 `onActivated`/路由进入时比对版本并重拉，另提供手动刷新与 60 秒可见时轮询。
10. **修改留痕不可篡改**：新增 `dr_change_log` 只追加不更新；以字段级增减（`add/remove/replace`）描述，避免保存整段历史正文。
11. **照片软删除 + 30 天回收站**：删除引用先标记 `deleted_at/purge_after`，列表过滤；到期任务清理本地文件与"本应用上传"的 Immich 资产，导入资产只删引用，避免误删用户相册原图。
12. **统计用绝对口径**：月度分布柱高 = 当月记录天数 ÷ 当月自然天数，纵轴固定 0-100%，柱顶常显"天数 · 比例"；不用最大值归一化。
13. **视觉留白优先**：统一 4/8 间距与 16px 卡片圆角，页面间距 24px、卡片内边距 20-24px；图表与图标共用主题变量，避免拥挤和风格漂移。
14. **图标自动匹配、可人工覆盖**：内置"情绪/标签/导航"映射表，按精确字典 → 关键词 → 类型默认 → 稳定哈希回退；标签表增加 `icon` 字段，用户可改。
15. **公网只走隧道**：宿主机 `cloudflared.exe` 是唯一入口，`web` 只监听 `127.0.0.1:9110`；Immich 不反代到公网，缩略图由后端代理；Cloudflare Access 作为可选第二道门，但不替代应用登录。
16. **照片库自动开通并按账号隔离**：OWNER 配置一次 Immich 管理员 Key；新账号注册后自动创建独立 Immich 用户、最小权限 Key 和默认相册，无需逐人操作。管理员 Key 与用户 Key 用 AES-256-GCM + 不同 AAD 加密，临时密码只在内存且开通后立即失效；未开通不降级到全局 Key。
17. **菜单即权限**：`t_um_resource` 同时表示菜单与分组，`t_um_role_resource` 保存角色可见菜单；前端侧栏完全由后端菜单树驱动，OWNER 固定拥有全部菜单，MEMBER 与自定义角色按授权展示。
18. **照片库表述面向用户**：普通用户界面统一使用"照片库"，不出现 Immich 术语；未接入照片库时明确提示"照片保存在服务器本机"，上传与记录不受影响。
19. **管理页可维护**：组织、菜单、角色菜单权限均提供可视化维护，接口仍在后端校验 OWNER 权限，不依赖前端隐藏。

## 8. 与 BigTrans 的复用清单

| 类别 | 直接借鉴 | 说明 |
|---|---|---|
| 系统表 | `com_userlist`、`t_um_user_role`、`t_um_role`、`t_um_org`、`t_um_user_org`、`t_um_resource`、`t_um_role_resource`、`cod_general_codes`、`t_switch` | 表名与公共字段保持一致 |
| 公共字段 | `id numeric(32,0)`、`insert_time/update_time`、`insert_user/update_user`、`version`、`org_id` | 业务表沿用，ID 以字符串返回 |
| 接口风格 | `{code,message,data}`、`code=200` 成功、`401/1003` 登录失效 | 前端请求封装直接复用 |
| 认证 | `Authorization` 放 JWT 原文、响应头 `token` 续签 | 增加会话登记与撤销 |
| 传输加密 | 前端 RSA 加密敏感字段，后端私钥解密 | 注册/改密/重置同样加密 |
| 前端 | 登录页流光卡片、BasicLayout、ThemeSelect、LangSelect、axios 封装、系统管理页模式 | 组件与样式可直接迁移 |
| 主题 | `--app-primary #2090ff`、深浅色变量、默认深色 | 保留平台视觉一致性 |

明确不借鉴：三次 Base64、SHA-256 存密码、全站 POST 之外的复杂租户/组织逻辑、Flink CDC、ctos3 注解体系。

## 10. 主要风险

| 风险 | 影响 | 对策 |
|---|---|---|
| Immich 凭据管理缺陷 | 跨账号看到照片或 Key 泄露 | 每账号独立 Immich 用户/Key；AES-GCM 加密；绑定/失效测试 |
| 自动开通被滥用 | 恶意注册批量创建 Immich 用户 | 仅 INVITE/OWNER 触发；默认注册 CLOSED；配额与限流 |
| 管理员 Key 泄露 | 开通权限被滥用 | 仅 OWNER 配置；最小权限；独立加密；可快速停用/轮换 |
| JWT 无法即时失效 | 改密后旧 token 仍可用 | 服务端会话登记 + `token_version`，每次请求校验 |
| RSA 传输被误认为足够安全 | 忽视 TLS 配置 | HTTPS 必须开启；RSA 只是纵深防御 |
| 老机器 CPU 推理慢 | 描述/总结等待久 | AI 后置；7B 量化、夜间批处理、并发为 1 |
| Immich 升级破坏 API | 导入/缩略图失效 | 固定版本、封装客户端、契约测试、升级前备份 |
| 单点家用网络/断电 | 服务不可用 | UPS、开机自启、每日备份到第二块盘或对象存储 |
| 账号被爆破 | 隐私泄露 | Argon2id、登录限流、失败锁定、强密码策略；隧道场景按 `CF-Connecting-IP` 取真实 IP |
| 数据丢失 | 无法恢复 | 每日 pg_dump + 照片目录增量备份 + 季度恢复演练 |
| 误删照片/记录 | 无法找回 | 30 天回收站 + 审计日志；导入的 Immich 原图永不由本应用删除 |
| 宿主机端口直连 | 绕过 Cloudflare Access/WAF、明文 HTTP | `web` 仅绑定 `127.0.0.1` 或仅 Docker 内网；防火墙拒绝 9110 入站 |
| Immich 管理面暴露 | 攻击面扩大、后台被扫描 | 取消公网 `/immich/` 反代；缩略图统一走后端代理 |
| 审计日志无限增长 | 占用存储、查询变慢 | 按年归档到冷表/文件；保留最近 2 年在线可查 |

## 11. 资源估算

- 存储：每天 3 张、每张 5MB，10 年约 55GB；视频另计，建议预留 200GB。
- 数据库：10 年、少量账号，记录与描述 < 1GB。
- 内存：Immich 约 2GB，PostgreSQL 约 512MB，FastAPI 约 512MB；Ollama 7B 量化约 6-8GB（可选）。
- 建议：16GB 内存、4 核以上；无 GPU 也可用，仅 AI 处理速度较慢。

## 12. 成功指标

- 连续记录 30 天，漏记不超过 2 天。
- 单次记录操作（上传 + 一句话）不超过 30 秒。
- 打开年视图到可交互不超过 1.5 秒（局域网）。
- 账号注册到完成首次记录不超过 2 分钟。
- 任意两个账号之间无法读取对方数据。
- 任意一次备份可在 1 小时内恢复出可访问的完整服务。
