## 1. 术语与约定

| 术语 | 含义 |
|---|---|
| 日记层 | 本项目自研的每日记录服务，不包含照片原文件管理 |
| 照片底座 | Immich，负责原文件、缩略图、EXIF、视频转码、CLIP、人脸 |
| 记录日 | 以 `Asia/Shanghai`（UTC+8）计算的本地日期，每个账号每天唯一一条记录 |
| 资产 | Immich 中的 `asset`，可能是图片或视频 |
| 描述 | 针对单张照片的一句话中文说明，来源为 AI、人工或 Immich 原有 description |
| 总结 | 针对周/月/年区间的多段 Markdown 回顾，属于 P2 能力 |
| 分桶 | 按周、月、自定义区间、标签、情绪、媒体类型聚合浏览 |
| 会话 | JWT 的 `jti` 与服务端 `dr_user_session` 登记记录，用于撤销与设备管理 |
| 修改留痕 | 对记录、照片、标签的每次写操作追加一条不可变的 `dr_change_log`，描述操作人、时间与字段级增减 |
| 照片回收站 | `photo` 软删除状态，保留 30 天，可恢复；到期后清理本地文件与"本应用上传"的 Immich 资产 |
| 签到率 | 某月记录天数 ÷ 该月自然天数，0-100% 的绝对比例，用于月度分布图 |
| Immich 凭据 | 每个应用账号绑定自己的 Immich 用户与 API Key，后端加密存储，按当前用户选择客户端 |

工程约定：

- 单仓库 monorepo：`backend/`、`frontend/`、`deploy/`、`docs/`。
- 后端使用 Python 3.12、FastAPI、SQLAlchemy 2.0、Alembic、Pydantic v2。
- 前端使用 Vue 3.5、Vite 5.4、antdv-next 1.8、Vuex 4、Vue Router 4.5（hash 模式）、Less；Node 固定 18.20。
- 系统基础表、公共字段、响应结构、认证方式与 BigTrans 对齐；不引入 ctos3、BeetlSQL、Flink。
- 外部系统（Immich、Ollama）只允许通过服务层访问，禁止业务代码直接拼 HTTP。
- 不直接读写 Immich 的数据库，只使用 Immich 官方 REST API。
- 所有容器设置 `TZ=Asia/Shanghai`；数据库使用 `timestamp` 存上海本地时间，接口输出 `yyyy-MM-dd HH:mm:ss`。
- Immich 管理员 Key 与用户 Key 使用 AES-256-GCM 加密存储，密钥只来自 `CREDENTIAL_ENCRYPTION_KEY`。

## 2. 背景与目标

### 2.1 背景

用户希望以照片为主要记忆锚点，记录每天至少一个瞬间，解决文字日记回看时记忆模糊、时间悄然流逝的问题。已有旧台式机可长期开机，具备自托管条件。服务需要具备账号注册登录、基础管理、加密传输等平台基础能力，并与已有 BigTrans 工程的表结构、接口风格和前端交互保持一致，降低维护与迁移成本。

### 2.2 目标

| 编号 | 目标 | 度量 |
|---|---|---|
| G1 | 极低摩擦完成每日记录 | 从打开到保存 ≤ 30 秒；≤ 3 次点击 |
| G2 | 不漏记、可坚持 | 连续记录 30 天，漏记 ≤ 2 天 |
| G3 | 回看有画面感 | 任意一天 2 次点击内看到照片与文字 |
| G4 | 账号与数据安全 | 密码 RSA 传输 + Argon2id 存储；任意两账号数据不可互读 |
| G5 | 数据自主可控 | 全量数据可导出；RPO ≤ 24h，RTO ≤ 4h |
| G6 | 随时随地访问 | 手机蜂窝网络可访问，HTTPS，未授权不可见 |
| G7 | AI 可插拔 | 未接入 AI 时，记录、上传、统计、浏览全部可用 |
| G8 | 与 BigTrans 一致 | 系统表名/字段、响应结构、JWT 请求头、前端视觉保持一致 |

### 2.3 非目标

- 公开社区、点赞评论、关注关系。
- 第三方 OAuth（Google/GitHub）登录，首版只做账号 + 密码。
- 通用相册管理（人脸合并、相册整理等交给 Immich）。
- 视频剪辑、照片修图。
- 云端 SaaS 与订阅计费。
- 复制 BigTrans 的 Flink 告警引擎、Kafka 上报、多租户组织树等业务。

## 3. 范围与优先级

### 3.1 MVP（必须）

1. 账号体系：注册、登录、退出、改密、会话列表与撤销、JWT 续签。
2. 基础管理：用户、角色、组织、字典、全局开关，沿用 BigTrans 表。
3. 数据隔离：每个账号只能访问自己的记录、照片引用、标签、统计。
4. 每日记录：文本、情绪、标签、照片/视频关联。
5. 上传：浏览器上传图片/视频，存储交给 Immich；每个应用账号自动开通独立 Immich 用户与 API Key。
6. 日历热力图与按月时间线。
7. 区间、标签、情绪筛选。
8. 统计：记录天数、照片数、连续天数、月度分布（天数 + 签到率）、情绪分布、标签 Top 12。
9. 从 Immich 按日期导入已有资产。
10. 部署与访问保护。
11. 数据同步：保存后跨页面自动刷新，手动刷新按钮，页面可见时 60 秒定时刷新。
12. 修改留痕：记录、照片、标签的每次新增/修改/删除都写审计日志。
13. 照片回收站：删除后保留 30 天，可恢复，到期自动清理。
14. 视觉规范：统一"每日记录"品牌名、间距/圆角体系、图标自动匹配与图表化展示。
15. 全自动照片库：OWNER 配置一次 Immich 管理员 Key，新账号自动开通独立 Immich 用户/Key/相册。

### 3.2 P1（上线后第一个迭代）

1. 回忆检索：照片语义搜索 + 日记全文搜索。
2. 全量导出（JSON/Markdown + 媒体清单）。
3. 邀请码注册、用户管理增强。
4. 自助找回密码（需配置 SMTP）。
5. 动态菜单与按钮权限（沿用 `t_um_resource` / `t_um_role_resource`）。

### 3.3 P2（后续）

1. AI 自动描述（图片）。
2. 周/月/年总结，手动与定时生成。
3. 视频关键帧描述。
4. 日记文本向量化与语义检索（pgvector）。
5. PWA 离线草稿、推送提醒。

## 4. 角色与权限

| 角色 | 能力 | 说明 |
|---|---|---|
| 所有者 `OWNER` | 全部读写、生成总结、导入、导出、管理用户与平台设置、维护菜单与角色权限 | 第一个注册账号自动成为 owner，`user_type='2'`；固定拥有全部启用菜单 |
| 成员 `MEMBER` | 管理自己的记录、照片引用、标签、导出自己的数据 | 不能查看他人数据，不能进管理页，`user_type='1'`；侧栏菜单由角色授权决定 |
| 自定义角色 | 按角色授权访问系统页面 | 菜单范围由 OWNER 在角色管理中勾选 |
| 运维者 | 部署、备份、恢复、查看日志 | SSH + 服务器账号，非应用角色 |
| 未登录访问者 | 仅注册页、登录页、公钥接口、健康检查 | 其余接口返回 1003 |

权限规则：

- 所有业务查询必须带 `user_id` 过滤，禁止仅按 `entry_date` 查询。
- 管理接口统一以 `/system/` 开头，校验角色 `OWNER` 或 `t_um_role.code='OWNER'`。
- 角色数据存 `t_um_role` / `t_um_user_role`，与 BigTrans 一致；`com_userlist.user_type` 仅作兼容标记。
- 菜单可见范围存 `t_um_resource` / `t_um_role_resource`；OWNER 不受授权表限制，始终可见全部启用菜单。
- `org_id` 字段保留并统一填默认组织 `1`，不参与数据隔离；隔离以 `user_id` 为准。

## 5. 功能需求

### FR-00 账号与认证

- 注册：登录账号 `userid`、显示名 `username`、邮箱、密码；三者唯一（邮箱可空？MVP 必填）。
- 首个注册账号自动成为 `OWNER`，之后注册模式自动切为 `closed`。
- 注册模式：`OPEN`（任何人可注册）、`INVITE`（需邀请码）、`CLOSED`（关闭注册），存 `t_switch` 的 `DAILYRECORD_REGISTER_MODE`。
- 登录：支持 `userid` 或邮箱 + 密码；密码在前端用 RSA 公钥加密后传输。
- 登录成功返回 JWT 与用户信息；JWT 放 `Authorization` 请求头，原文，不加 `Bearer`。
- 剩余有效期 ≤ 1 小时时，响应头 `token` 下发新 token，前端自动替换。
- 退出：撤销当前会话登记；支持"退出全部设备"。
- 修改密码：验证旧密码；成功后撤销其他所有会话并使旧 token 失效。
- 会话管理：查看设备、最近活跃时间、IP（脱敏）、撤销单个或全部。
- 密码存储：Argon2id；禁止明文、可逆加密、MD5/SHA1。
- 登录保护：失败计数、临时锁定、按 IP 与账号双维度限流。
- 传输保护：RSA-2048 加密密码字段；HTTPS 必须开启。

验收：

1. 抓包只能看到 RSA 密文，看不到明文密码。
2. 数据库中 `password` 以 `$argon2id$` 开头，任何接口都不返回密码与哈希。
3. 两个账号各自创建记录，互相调用详情接口返回 404 或空数据。
4. 修改密码后，其他设备的旧 token 立即失效。
5. 连续 5 次密码错误后账号锁定 15 分钟。
6. 注册关闭时，注册接口返回 `1007 REGISTRATION_CLOSED`。
7. 无 token 或 token 过期返回 `1003`。

### FR-01 每日记录

- 每个账号每天最多一条记录，以 `(user_id, entry_date)` 唯一约束。
- 字段：记忆点文本（≤ 5000 字）、情绪（字典 `MOOD`）、标签（≤ 20 个）、照片列表、封面。
- 首次进入某天时展示空状态，不自动写库；保存后创建记录。
- 支持前端 localStorage 草稿；正式保存以服务端为准。
- 删除记录时默认保留照片引用（转为未关联），需二次确认。
- 并发编辑使用 `version` 字段做乐观锁：提交时带 `version`，冲突返回 `1009 VERSION_CONFLICT`。
- 每次创建、更新、删除写一条 `dr_change_log`；更新时只记录发生变化的字段，内容以增减描述：
  - 文本：`field=note`，记录新增片段、删除片段与前后长度，不重复存整段正文。
  - 标签：`field=tags`，记录 `added[]` / `removed[]`。
  - 情绪/封面：`field=mood|cover`，记录 `before` / `after`。
  - 照片关联：`field=photos`，记录 `addedPhotoIds[]` / `removedPhotoIds[]`。
- 保存响应返回最新 `version` 与 `changedFields`，前端据此更新全局数据版本并刷新其他页面。
- 提供"修改记录"入口：按天查看该条记录的全部变更，按时间倒序，展示操作人显示名、时间、增减内容。

验收：

1. 同一天重复保存为更新，不产生重复行，`version` 自增。
2. 标签去重、去首尾空格、自动去掉前导 `#`。
3. 保存后刷新页面，内容与照片顺序一致。
4. 并发两个标签页编辑同一天时，后提交者收到 `1009` 并提示刷新。
5. 账号 A 无法通过修改 URL 或 ID 读取账号 B 的某天记录。
6. 同一内容连续保存两次，第二次不产生无变化的审计日志。
7. 修改文本、标签、情绪、封面、照片关联各一次，审计日志能准确还原"加了什么、删了什么"。
8. 审计日志无更新/删除接口；普通账号只能读取自己的记录历史。

### FR-02 照片与视频

- 支持一次多选上传，单文件默认 ≤ 100MB（Cloudflare Tunnel 单请求上限；局域网直连可临时调到 200MB）；图片 JPEG/PNG/WebP/HEIC，视频 MP4/MOV/WebM。
- 上传、缩略图、原图必须使用当前登录账号绑定的 Immich 凭据；未绑定返回 `1013`，前端引导去账户设置绑定。
- 上传时若 Immich 可用，则上传到该账号自己的 Immich 用户与相册；不可用时拒绝并提示（生产模式）。
- 开发模式允许本地磁盘存储，用于无 Immich 环境联调。
- 同一账号重复导入同一 Immich 资产时按 `(user_id, immich_asset_id)` 去重。
- 每个记录最多 1 个封面；取消封面后允许无封面。
- 支持编辑描述、调整拍摄时间、删除引用；默认不删除 Immich 原文件。
- 视频缩略图由 Immich 负责，前端统一走缩略图接口。
- 删除照片 = 移入回收站（软删除）：`deleted_at` 置为当前时间，`purge_after = deleted_at + 30 天`，同时解除记录关联与封面；列表、统计、时间线立即不再展示。
- 回收站内 30 天内可恢复（恢复时若原记录仍在则重新关联，否则作为未关联照片）。
- 到期清理规则：
  - 本应用上传到 Immich 的资产（`photo.origin='upload'`）：调用 Immich API 永久删除该资产。
  - 从 Immich 导入的资产（`photo.origin='import'`）：只删除日记层引用与 `photo` 行，**永不删除 Immich 原图**。
  - 本地存储（`storage_kind='local'`）：删除磁盘文件与 `photo` 行。
- 清理任务每天执行一次（容器内定时或宿主机 cron），并写入 `dr_job_run` 与审计日志；失败重试 3 次后告警。
- 删除记录本身不进入照片回收站；照片引用转为未关联，保留原文件。

验收：

1. 上传 5 张图片后，记录页按拍摄时间升序展示，首张自动成为封面。
2. 重复导入同一天 Immich 资产不产生重复照片。
3. 视频显示占位缩略图，可点击播放原文件。
4. 上传中断或 Immich 返回错误时，前端显示可重试提示，数据库无半条记录。
5. 账号 A 的照片 ID 无法被账号 B 读取缩略图或原图。
6. 删除照片后，时间线、统计、照片列表立即不可见；30 天内可在回收站恢复。
7. 把 `purge_after` 调到过去时间执行清理任务：本地文件与本应用上传的 Immich 资产被删除，导入资产原图仍在。
8. 清理任务失败不会误删未到期照片，错误写入 `dr_job_run.error`。

### FR-03 日历与时间线

- 年视图热力图：365/366 格，颜色按当天照片数或是否有记录分档。
- 月视图：按日期分组，显示封面缩略图、首行文字、标签、照片数。
- 点击日期进入当天编辑页。
- 支持键盘左右切换月份。
- 数据刷新：
  - 路由进入、`KeepAlive` 激活时，比较全局 `dataVersion.entries` 与本地已渲染版本，不一致则重拉。
  - 页面标题右侧提供"刷新"按钮（带最近更新时间）；手动刷新同时更新全局版本。
  - 页面可见（`document.visibilityState === 'visible'`）时每 60 秒静默刷新一次；隐藏时暂停，恢复可见立即刷新一次。
  - 保存、上传、删除、导入成功后由调用方递增 `dataVersion.entries` 与 `dataVersion.stats`。

验收：

1. 热力图单元格数量与当年天数一致，闰年 366。
2. 有记录但无照片的日期显示"文字记录"样式。
3. 点击任意格子进入对应日期，URL 可分享给本人其他设备。
4. 东八区 00:00 至 01:00 上传的照片，归属当天而不是前一天。
5. 在今天页保存后切到时间线，无需手动刷新即可看到最新记录。
6. 手动刷新按钮可触发请求，并显示刷新时间。
7. 页面隐藏 5 分钟后回到前台，自动刷新一次；期间不产生轮询请求。

### FR-04 筛选与分桶

- 维度：起止日期、标签、情绪、媒体类型（图片/视频/有描述）、关键词。
- 预设：本周、本月、近 30 天、今年、自定义。
- 结果按日期倒序，使用 BigTrans 风格的分页请求。
- 筛选条件写入 URL query，刷新保持。
- "周"以周一开始，按东八区计算。

验收：

1. 组合条件为 AND 语义。
2. 空结果展示空状态与清除筛选入口。
3. 1000 条记录下筛选响应 p95 ≤ 500ms。
4. 跨年周（12 月 29 日至 1 月 4 日）归属正确。

### FR-05 统计与签到

- 指标：记录天数、照片数、文字总量、当前连续天数、最长连续天数、月度分布、情绪分布、标签 Top 12。
- 连续天数定义：有记录或有照片的日期算签到；今天未记录时从昨天起算，不立即断签。
- 年视图与月视图数字一致。
- 所有统计按当前登录账号计算。
- 月度分布口径：
  - 每月返回 `days`（记录天数）、`daysInMonth`（当月自然天数，闰年 2 月为 29）、`rate`（`days / daysInMonth`，0-1，保留 4 位小数）。
  - 柱状图纵轴固定 0-100%，柱高 = `rate × 100%`，**不做全年最大值归一化**。
  - 每根柱顶常显"18 天 · 58%"；未到的月份显示 0 天 0%，当年未开始/已结束时同样按自然天数计算。
  - 悬浮/聚焦显示"记录 18 天 / 30 天"；图表下方提供同数据表格，保证数字可读与可访问。
- 图表范围：月度签到率柱状图、情绪分布环形图、标签 Top 12 横向条、近 30 天记录折线；数字始终可见。

验收：

1. 构造跨月、跨年数据，连续天数计算正确。
2. 删除某天记录后统计实时更新。
3. 统计接口在 10 年数据量下 p95 ≤ 500ms。
4. 2024 年 2 月满勤显示"29 天 · 100%"，2026 年 2 月满勤显示"28 天 · 100%"。
5. 某月 15 天有记录、当月 30 天，柱高恰为 50%，柱顶显示"15 天 · 50%"。
6. 月度柱高不随其他月份的最大值变化；切换年份时同一月份的口径一致。

### FR-06 Immich 导入

- 普通用户界面统一称"照片库"，不出现 Immich 术语；仅系统设置对管理员展示"照片库（Immich）"。
- 选择日期后列出该日**当前账号自己照片库**的资产，标记已导入；不会返回其他应用账号的照片。
- 未接入照片库时，入口保留并提示"照片库未接入，照片仍保存在服务器本机"；接入后恢复导入能力。
- 支持全选导入或勾选导入。
- 导入后自动关联到该日记录（不存在则创建空记录），首张设为封面。
- 账号未绑定 Immich 时，入口隐藏；Immich 不可用时置灰并说明原因。

验收：

1. 导入 10 张资产后，日记库出现 10 条照片引用，Immich 原文件不变。
2. 重复导入同一批资产，返回 0 条新增。
3. Immich 超时返回 `1010 IMMICH_UNAVAILABLE`，前端提示稍后重试。

### FR-07 回忆检索（P1）

- 照片语义搜索：调用 Immich CLIP 搜索，返回资产并定位到日期。

### FR-08 导出与备份（P1）

- 导出 Markdown：按年/月生成目录与每日文件。
- 导出不包含原文件；原文件由 Immich 负责备份。
- 导出仅限当前账号数据；OWNER 可执行全量备份脚本。

### FR-09 AI 自动描述（P2，可选）

- 平台开关 `DAILYRECORD_AI_ENABLED` 默认 `N`；关闭时不启动 Worker，接口返回 `1011 AI_DISABLED`。

- Worker 调用本地 VLM，生成 ≤ 40 字中文描述。
- 描述写回日记库；可选写回 Immich `description`，不覆盖人工描述。
- 人工编辑描述后状态标记为 `manual`，不再被 AI 覆盖。

验收：

1. 开启 AI 并上传照片，有 GPU 时 60 秒内、CPU 时 5 分钟内出现描述。
2. 关闭 AI 或 Ollama 停止时，上传与记录不受影响。
3. 30 张评测集人工可接受率 ≥ 85%，无人物身份猜测。

### FR-10 周/月/年总结（P2，可选）

- 同一账号同一周期重复生成时覆盖旧内容，保留 `prompt_version` 与模型名。
- 内容结构：三句话概括、3-5 个值得记住的片段、一句话回顾。
- 无记录时拒绝生成并提示；AI 未开启时返回 `1011`。

验收：

1. 生成结果只包含素材中出现的事件。
2. 1 月 2 日生成上一年总结时，范围正确。
3. 关闭 AI 时按钮置灰并说明原因。

### FR-11 修改留痕（MVP）

- 覆盖对象：每日记录（创建/更新/删除）、照片引用（关联/解除/描述/封面/回收/恢复/清理）、标签（创建/改名/挂载变化）。
- 审计表 `dr_change_log` 只追加，不提供更新与删除接口；数据库账号无 `UPDATE/DELETE` 该表的业务权限（可选加固）。
- 每条日志字段：`user_id`、`operator_id`、`operator_name`、`entity_type`、`entity_id`、`entry_id`、`entry_date`、`action`、`changes`（JSONB）、`request_id`、`ip`、`user_agent`、`created_at`。
- `changes` 采用字段级增量：

```json
[
  {"field": "note", "op": "update", "added": "，傍晚下了小雨", "removed": "", "beforeLength": 42, "afterLength": 50},
  {"field": "tags", "op": "update", "added": ["雨天"], "removed": ["江边"]},
  {"field": "mood", "op": "replace", "before": "平静", "after": "开心"},
  {"field": "photos", "op": "update", "added": ["1839..."], "removed": ["1840..."]}
]
```

- 文本 diff 使用行内最小差异（前后缀裁剪 + 中间片段），单条日志的文本片段合计 ≤ 2000 字，超出部分只记录长度与摘要。
- 同一次保存只写一条日志，包含多个字段变化；无实际变化不写日志。
- 查看入口：今天页"修改记录"抽屉、时间线当天详情；按时间倒序分页。
- 保留策略：在线保留 2 年；更早归档到 `dr_change_log_archive` 或压缩文件，不随记录删除而删除。

验收：

1. 修改记录后，历史中能看到操作人、时间、字段、增删内容。
2. 仅修改标签时，日志不包含正文片段。
3. 删除记录后，历史仍可查询该次删除动作与删除时的摘要。
4. 并发保存触发 `1009` 时不写审计日志。
5. 账号 A 无法读取账号 B 的修改历史。

### FR-12 照片回收站（MVP）

- 入口：今天页照片区"回收站"、账户设置中的"回收站"；显示剩余天数、缩略图、原日期、删除时间、操作人。
- 支持单个恢复、批量恢复、立即彻底删除（二次确认，仅 OWNER 或本人）。
- 回收站照片不参与日历、时间线、统计、导出中的媒体计数；导出可附带 `trash` 清单（P1）。
- 清理任务：
  - 每日 03:30（东八区）执行，扫描 `deleted_at IS NOT NULL AND purge_after <= now()`。
  - 单次批量上限 500，逐条处理并记录结果；失败重试 3 次，仍失败保留记录并告警。
  - 清理完成写 `dr_job_run`（`job_name='photo_purge'`，`run_key=YYYY-MM-DD`）与 `dr_change_log`（`action='PURGE'`）。
- 恢复时若原记录已删除，照片作为未关联素材保留，用户可再挂载。
- 回收站数据计入存储容量提示，但 30 天内不主动删除任何原文件。

验收：

1. 删除照片后立即可在回收站看到，剩余天数显示 30 天递减。
2. 恢复后照片回到原记录（记录存在时），封面不被自动恢复，需用户重设。
3. 彻底删除立即移除文件与数据库行，并写审计日志。
4. 到期任务只清理到期项，未到期项不受影响。
5. 从 Immich 导入的照片到期后，Immich 原图仍可访问。

### FR-13 全自动 Immich 开通与凭据隔离（MVP）

> v1.5 已落地：Compose 内置 Immich v1.135.3（`ghcr.nju.edu.cn` 镜像），管理员 Key 由 `scripts/init_immich.py` 初始化；注册后自动创建 Immich 用户、最小权限 Key 与相册，用户 Key 用 AES-256-GCM 加密存储；老账号打开账户设置或首次上传时补开通。

- 目标：多人使用时照片库按应用账号隔离；新账号自动获得独立 Immich 用户与 API Key，管理员无需逐人手动操作。
- 角色划分：
  - OWNER 在系统设置中配置一次 Immich 管理员凭据，仅用于"开通/修复"。
  - 日常上传、搜索、导入、缩略图、原图使用各账号自己的最小权限 Key。
- 管理员凭据：
  - 字段：Immich URL（默认 `IMMICH_URL`）、管理员 API Key、启用开关。
  - 权限最小化：`adminUser.create`、`adminUser.update`（重置临时密码）；不授予 `adminUser.delete`、资产读取等日常权限。
  - 加密存储，接口只返回后 4 位；只有 OWNER 可配置，任何角色都不能读取明文。
  - 失效时自动开通停止，回退到手动绑定，不影响已有账号的日记文字。
- 自动开通流程（新应用账号创建后触发）：
  1. 生成高熵临时密码（`secrets.token_urlsafe(32)`），仅保存在内存。
  2. 用管理员凭据调用 Immich `POST /api/admin/users`，`email` 取应用邮箱，`name` 取显示名，`isAdmin=false`。
  3. 调用 `POST /api/auth/login`，用临时密码换取 Immich access token（内存）。
  4. 调用 `POST /api/api-keys` 创建最小权限 Key：`asset.read`、`asset.upload`、`album.read`、`album.create`、`album.update`；不授予管理权限。
  5. 用新 Key 创建/复用相册 `每日记录-{userid}`，记录 `album_id`。
  6. 用管理员接口把 Immich 密码重置为新的随机值并丢弃，使临时密码立即失效；用户仅通过每日记录访问照片。
  7. 用 AES-256-GCM 加密 Key 落库，`status=active`、`provision_status=active`；清空内存中的密码与 token。
- 不落地原则：
  - Immich 密码、access token、API Key 明文禁止写入数据库、日志、审计、错误响应、前端状态。
  - 管理员 Key 与用户 Key 使用不同 AAD（`immich:admin` / `immich:user:{user_id}`），密文不可互换。
  - Immich 错误统一脱敏为"照片库开通失败，请稍后重试"+ `requestId`。
- 失败与重试：
  - Immich 不可用/超时：应用账号仍可用；`provision_status=pending/failed`，后台每 5 分钟重试，最多 3 次，之后由 OWNER 手动重试。
  - Immich 已存在同邮箱用户：不自动接管，标记 `failed`，提示 OWNER 处理；避免把他人 Immich 账号绑过来。
  - Immich 用户已创建但 Key 创建失败：保留 `immich_user_id`，通过管理员重置密码后重试；不删除已有 Immich 用户。
  - 提供 `POST /immich/credential/retry`（本人或 OWNER）与系统设置"为已有用户补开通"；OWNER 配置管理员 Key 后先给自己补开通。
- 配额与滥用防护：
  - 只有 `INVITE` 注册或 OWNER 创建账号触发自动开通；`OPEN` 注册默认不触发。
  - 全局默认最多 20 个自动开通账号，可在系统设置调整；按账号与 IP 限流。
  - 自动开通失败、重试、配额超限都写审计日志，但不记录任何密钥材料。
- 运行时：
  - 所有 Immich 调用按当前 `user_id` 取凭据；没有凭据返回 `1013`，Key 失效返回 `1014`。
  - 存储层读取照片（缩略图/原图）也必须按 `photo.user_id` 取凭据，不能使用全局客户端。
  - 所有者可"重置绑定"（清空凭据）但不能查看他人 Key；重置后用户可重新自动/手动绑定。
- 迁移：
  - 原 `IMMICH_API_KEY` 加密写入 OWNER 的凭据；其他旧账号由 OWNER 触发"补开通"，旧共享资产需重新导入。
  - 迁移脚本输出无法归属的旧照片清单。

验收：

1. 邀请码注册新账号后无需管理员操作，账户设置显示照片库 `active`。
2. A、B 自动开通后，B 的按日期搜索与缩略图都无法看到 A 的照片。
3. 断开 Immich 时注册，账号可用且照片库为 `failed`；Immich 恢复后自动重试成功。
4. 数据库、日志、审计、接口响应中均无明文 Immich 密码、token、API Key。
5. Immich 已存在同邮箱用户时标记 `failed`，不接管、不删除。
6. 关闭自动开通或管理员 Key 失效时，回退手动绑定，文字记录不受影响。
7. 超过配额或非 INVITE/OWNER 来源的注册不触发自动开通。

### FR-14 角色与菜单权限（MVP）

- 菜单表 `t_um_resource` 同时表示菜单与分组：`pid` 组成层级，`web_url` 为前端路由（分组为空），`icon_name` 为图标名，`sort` 排序，`enable` 控制启停。
- `t_um_role_resource` 保存角色可见菜单；保存时覆盖该角色的全部授权。
- OWNER 固定拥有全部启用菜单，不受授权表限制；MEMBER 与自定义角色按授权展示。新建菜单默认不授权给普通角色。
- 菜单管理：新增、编辑、删除；存在子菜单时禁止删除；删除菜单同步清理角色授权。
- 角色菜单权限：树形勾选、父子联动；父分组半选时仍保留分组，保证子菜单可以显示。
- 前端 `POST /auth/me` 返回当前用户菜单树；侧栏与移动端 Tab 均由菜单树渲染，未授权菜单不出现。
- 后端校验：菜单与角色授权接口仅 OWNER 可调用；普通用户即使直接修改 URL，`/System/*` 路由守卫与后端权限仍会拦截。

验收：

1. MEMBER 不勾选“系统管理”及其子菜单后，登录侧栏不显示该分组与子页面。
2. 勾选“用户管理”后，MEMBER 侧栏出现该菜单；OWNER 始终可见全部菜单。
3. 新增菜单后无需改代码即可出现在被授权角色的侧栏。
4. 删除有子菜单的菜单被拒绝；删除叶子菜单后相关角色授权同步清除。
5. 非 OWNER 调用 `/system/menu/*` 返回 403。

### FR-15 组织管理（MVP）

- 字段：组织编码、组织名称、上级组织、状态、备注；沿用 `t_um_org`。
- 支持新增、编辑、停用/启用、删除；组织编码唯一。

验收：

## 7. 技术选型

### 7.1 后端：Python FastAPI vs Java Spring Boot

| 维度 | Python + FastAPI | Java（复用 BigTrans：Spring Boot 2.6 + JDK 11 + ctos3） |
|---|---|---|
| AI/图像生态 | 强，Ollama、Pillow、ffmpeg 封装直接 | 中，需要额外进程或 SDK |
| 复用 BigTrans 基础模块 | 复用表结构与接口语义，代码重写 | 可直接移植部分 `zymonitor-system-biz` |
| 依赖负担 | 轻，无 ctos3/BeetlSQL | 需私有 Maven、ctos3、JDK 11 |
| 开发速度 | 快 | 中，工程结构重 |
| 运行时资源 | 较低 | 较高（JVM） |
| 结论 | **采用** | 备选 |

结论：保留 Python + FastAPI，按"同表、同响应、同认证、同界面"的方式与 BigTrans 对齐。若后续决定直接复用 `zymonitor-system-biz` 的 Java 实现，可只替换后端，数据库与前端契约不变。

### 7.2 前端：Vue 3 + antdv-next（直接借鉴 zymonitor-web）

| 组件 | 选型 | 对应 BigTrans |
|---|---|---|
| 框架 | Vue 3.5 | `vue ^3.5` |
| 构建 | Vite 5.4 | `vite ^5.4`，兼容 Node 18.20 |
| UI | antdv-next 1.8 | `a-*` 短标签、全局默认值 |
| 状态 | Vuex 4 | `auth` / `route` / `dict` |
| 路由 | Vue Router 4.5，hash 模式 | `createWebHashHistory` |
| 请求 | axios 封装 `Post/Get` | `src/api/axios.js` |
| 样式 | Less + `--app-*` 变量 | `styles/theme.less`、`modules.css` |
| 图标 | @iconify/vue | `SvgIcon`、`renderMenuIcon` |
| 时间 | dayjs | 已引入 |
| 登录背景 | FloatingLines（three.js） | `components/FloatingLines.vue` |
| 图表 | ECharts 6 + vue-echarts | 统计页与趋势图必备 |

运行环境：Node **18.20.x**（`engines` 固定 `18.20.x`），npm 10.x；后端 Python 3.12。

Node 18 下的依赖约束：

### 8.3 关键数据流

**注册与登录**

1. 前端请求 `GET /api/auth/publicKey` 获取 RSA 公钥（可缓存）。
2. 用户输入密码，前端 `jsencrypt` 公钥加密，得到 Base64 密文。
3. `POST /api/auth/login`，body 中 `password` 为密文。
4. 后端私钥解密，Argon2id 校验。
5. 生成 JWT，写入 `dr_user_session` 登记，返回 `{token, userInfo}`。
6. 前端把 token 放 `Authorization` 原文；后续请求自动携带。
7. 剩余有效期 ≤ 1h 时，响应头 `token` 下发新 token，前端替换。

**上传**

1. 前端 `POST /api/photo/upload`（multipart）。
2. API 校验 JWT、大小与 MIME，流式写入临时文件。
3. 调用 Immich `POST /api/assets` 上传，必要时加入指定相册。
4. 成功后写入 `photo`（`user_id`、`immich_asset_id`、`ai_state=disabled`）。
5. P2 开启 AI 后，Worker 轮询待描述照片，生成描述并写回。

**回看**

1. 前端 `POST /api/entry/calendar` 获取当前账号全年聚合。
2. 点击日期 `POST /api/entry/get`，缩略图走 `GET /api/photo/thumbnail/{id}`。
3. 缩略图由 API 校验归属后代理 Immich，nginx 缓存 7 天。

### 9.2 有意差异

| 项目 | BigTrans | 本项目 | 原因 |
|---|---|---|---|
| 后端框架 | Java 11 + Spring Boot 2.6 + ctos3 + BeetlSQL | Python 3.12 + FastAPI + SQLAlchemy | 避免私有框架绑定；AI 生态更顺 |
| 密码落库 | SHA-256（RSA 解密后） | Argon2id | 抗 GPU 爆破，行业推荐 |
| 密码二次处理 | 三次 Base64 | 去掉 | 可逆混淆不提供安全价值 |
| 传输加密范围 | 仅登录 RSA | 登录、注册、改密、重置全部 RSA | 统一敏感字段保护 |
| 认证 | JWT，无服务端登记 | JWT + `dr_user_session` | 支持设备列表、单设备撤销、全部撤销 |
| 时间字段 | `timestamp` + `yyyy-MM-dd HH:mm:ss` | 同样 `timestamp` + 上海时间，接口同格式 | 保持一致，满足东八区要求 |
| 主键 | `numeric(32,0)` 雪花 | 同样 `numeric(32,0)`，应用生成雪花 | 保持一致，ID 以字符串返回 |
| 组织 | 多组织 + 租户隔离 | 默认组织 `1`，不参与隔离 | 家庭场景不需要多租户 |
| 前端范围 | 桌面大屏，最小宽度 1200 | 桌面 + 移动端自适应 | 手机随时记录是核心场景 |
| 动态菜单 | 完整动态路由 | MVP 静态路由，P1 接动态菜单 | 降低首版复杂度 |

## 10. 数据设计

### 10.1 命名与公共字段

- 系统表沿用 BigTrans：`com_userlist`、`t_um_*`、`cod_general_codes`、`t_switch`。
- 业务表使用单数名词：`daily_entry`、`photo`、`tag`、`entry_tag`、`daily_summary`。
- 应用支撑表使用 `dr_` 前缀：`dr_user_session`、`dr_login_log`、`dr_job_run`、`dr_invite_code`、`dr_change_log`、`dr_change_log_archive`、`dr_immich_credential`、`dr_immich_admin_credential`。
- 业务表公共字段：

```sql
id          numeric(32,0) PRIMARY KEY,
insert_time timestamp,
update_time timestamp,
insert_user varchar(64),
update_user varchar(64),
version     numeric(19,0) NOT NULL DEFAULT 0,
org_id      numeric(32,0) NOT NULL DEFAULT 1
```

- ID 使用应用层雪花算法生成，接口序列化为字符串，避免前端精度丢失。
- 状态字段沿用 `Y/N` 短码；业务状态用字典 `cod_general_codes`。
- 时间字段为 `timestamp`（无时区），存上海本地时间。

### 10.2 系统表复用与扩展

系统表 DDL 直接使用 BigTrans `sql/init.sql`，本项目只做以下扩展：

```sql
-- 用户主档扩展
ALTER TABLE com_userlist ADD COLUMN email varchar(255);
ALTER TABLE com_userlist ADD COLUMN password_algo varchar(16) NOT NULL DEFAULT 'argon2id';

ALTER TABLE com_userlist ADD COLUMN locked_until timestamp;
ALTER TABLE com_userlist ADD COLUMN token_version numeric(19,0) NOT NULL DEFAULT 0;
ALTER TABLE com_userlist ADD COLUMN timezone varchar(64) NOT NULL DEFAULT 'Asia/Shanghai';
ALTER TABLE com_userlist ALTER COLUMN password TYPE varchar(255);

CREATE UNIQUE INDEX uq_com_userlist_userid ON com_userlist (lower(userid));
CREATE UNIQUE INDEX uq_com_userlist_email ON com_userlist (lower(email)) WHERE email IS NOT NULL;
```

字段语义：

| 字段 | 说明 |
|---|---|
| `userid` | 登录账号，2-32 位字母数字下划线或中文，唯一 |
| `username` | 显示名 |
| `email` | 邮箱，注册必填，唯一 |
| `password` | Argon2id 哈希 |
| `password_algo` | 固定 `argon2id`，便于未来升级 |
| `user_active` | `Y` 启用 / `N` 禁用 |
| `user_type` | `1` 成员 / `2` 所有者（兼容 BigTrans） |
| `token_version` | 全设备失效版本号，改密/禁用时 +1 |
| `failed_login_attempts` | 连续失败次数 |
| `locked_until` | 锁定截止时间 |
| `login_time` | 最近登录时间 |
| `timezone` | 默认 `Asia/Shanghai` |
| `org_id` | 默认 `1`，不参与隔离 |

角色与组织：

- `t_um_role` 种子：`OWNER`（所有者）、`MEMBER`（成员）。
- `t_um_user_role` 关联用户与角色。
- `t_um_org` 种子：`id=1, org_code='DEFAULT', org_name='默认组织'`。
- `t_um_user_org` 每个用户关联默认组织。
- `t_um_resource` / `t_um_role_resource`：MVP 仅存系统管理菜单，P1 启用动态菜单。
- `cod_general_codes` 种子字典：`MOOD`、`MEDIA_TYPE`、`TAG_KIND`、`PERIOD_TYPE`、`REGISTER_MODE`、`LOGIN_RESULT`、`AI_STATE`。
- `t_switch` 种子：`DAILYRECORD_REGISTER_MODE=CLOSED`、`DAILYRECORD_AI_ENABLED=N`、`DAILYRECORD_BOOTSTRAP_DONE=N`、`DAILYRECORD_IMMICH_AUTO_PROVISION=Y`、`DAILYRECORD_IMMICH_PROVISION_LIMIT=20`。

### 10.4 数据规则

- `entry_date` 按 `Asia/Shanghai` 计算，不使用数据库服务器时区。
- `taken_at` 优先取 Immich `localDateTime`/EXIF，缺失时取上传时间。
- 描述来源优先级：`manual` > `ai` > `immich`；`manual` 不被 AI 覆盖。
- 删除记录：`photo.entry_id` 置空，不级联删除照片引用；删除照片引用不删除 Immich 原文件。
- 每张照片最多属于一条记录；如需跨天引用，复制引用记录。
- 所有业务表读写必须带 `user_id` 条件；管理端跨用户查询需显式进入 `/system/` 模块。
- 乐观锁：更新时 `WHERE id=? AND version=?`，成功后 `version=version+1`；失败返回 `1009`。
- 删除照片采用软删除：`deleted_at=now()`、`deleted_by=操作人`、`purge_after=now()+30 天`，`entry_id` 置空、`is_cover=false`；所有列表默认 `deleted_at IS NULL`。
- 回收站恢复：`deleted_at/deleted_by/purge_after` 置空；原记录仍在时回填 `entry_id`，封面不自动恢复。
- 清理任务条件：`deleted_at IS NOT NULL AND purge_after <= now()`；清理前再次确认无其他引用。
- `photo.origin='import'` 的资产永不调用 Immich 删除接口；`origin='upload'` 才允许删除应用创建的资产。
- 审计日志在业务事务内写入，与业务变更同提交；业务回滚则日志不落库。
- 审计日志只追加；应用层不提供修改/删除接口，归档走 `dr_change_log_archive`。
- Immich 凭据每个 `user_id` 最多一条；所有 Immich 请求按当前用户取凭据，禁止回退到全局 Key。
- 加密算法统一 AES-256-GCM：`CREDENTIAL_ENCRYPTION_KEY` 为 32 字节 Base64；密文格式 `v1:<nonce_b64>:<cipher_b64>`。
- 管理员 Key 的 AAD 为 `immich:admin`；用户 Key 的 AAD 为 `immich:user:{user_id}`，密文不可互换。
- 明文密钥只存在于请求/开通流程内存；禁止写数据库、日志、审计、异常信息、前端状态。
- 绑定校验调用 Immich `GET /api/users/me`；Key 权限按 FR-13 最小化，不使用 Immich 管理员 Key 做日常读写。
- 自动开通只由 INVITE 注册或 OWNER 创建账号触发；`OPEN` 注册、超配额、管理员 Key 失效时不触发。
- 未配置管理员 Key 时不创建凭据行；账号仍可注册，稍后由 OWNER 补开通或用户手动绑定。
- 临时 Immich 密码只存在内存，开通成功后由管理员接口重置为新的随机值并丢弃；不保存、不返回、不写日志。
- 开通失败置 `provision_status='failed'`，记录脱敏后的 `last_provision_error`；重试最多 3 次，不自动删除已创建的 Immich 用户。
- Key 失效置 `status='invalid'` 并记录 `last_error`；解绑删除凭据行，但保留 `photo` 引用与 Immich 原图。
- 更换加密主密钥时，先配置新旧双 Key，再批量重加密并递增 `key_version`，最后移除旧 Key。

### 10.5 迁移策略

- Alembic 管理业务表与扩展字段；系统表首版可直接执行 BigTrans `init.sql` 后打补丁。
- v1.3 迁移顺序：
  1. `photo` 增加 `origin`（默认 `'import'`，用于回填历史数据，避免被清理任务误删）、`deleted_at`、`deleted_by`、`purge_after`。
  2. 新建 `dr_change_log` 与 `dr_change_log_archive`，索引与 10.3 一致。
  3. `tag` 增加 `icon varchar(32)`。
  4. 新上传代码显式写 `origin='upload'`；导入代码显式写 `origin='import'`。
  5. 新建 `dr_immich_credential` 与 `dr_immich_admin_credential`；若存在 `IMMICH_API_KEY`，加密写入 OWNER 的凭据并沿用原相册。
  6. 迁移脚本输出"非 OWNER 且引用了 OWNER Immich 资产"的照片清单；这些用户由 OWNER 触发自动补开通后重新导入，旧引用暂时只读/占位。

- 每次发布前 `pg_dump`；回滚先恢复数据库再回滚镜像。
- 破坏性变更采用"双写/回填/切换"三步，禁止直接 `DROP COLUMN`。

## 11. 时间与东八区处理

### 11.1 原则

- 业务时区固定为 `Asia/Shanghai`（UTC+8，无夏令时）。
- 数据库使用 `timestamp`（无时区），存上海本地时间；连接会话设置 `SET TIME ZONE 'Asia/Shanghai'`。
- 接口日期时间统一 `yyyy-MM-dd HH:mm:ss`，日期统一 `yyyy-MM-dd`，与 BigTrans 序列化一致。
- `entry_date` 是上海日期，用于唯一约束、日历、统计、总结边界。
- 周从周一开始；月、年按上海自然边界。
- 前端不依赖设备时区做日期归属。

### 11.2 实现要求

| 层 | 要求 |
|---|---|
| 容器 | 所有服务设置 `TZ=Asia/Shanghai` |
| 数据库 | 连接初始化执行 `SET TIME ZONE 'Asia/Shanghai'`；DDL 使用 `timestamp` |
| 后端 | 禁止 `datetime.now()` 裸调用；统一 `now_shanghai()` / `today_shanghai()` |
| API | 时间字段 `yyyy-MM-dd HH:mm:ss`；日期字段 `yyyy-MM-dd` |
| 前端 | 日期字符串直接展示，不做 UTC 转换；需要计算时用 dayjs 按上海时区处理 |
| 上传 | `entry_date` 缺省时取上海当天；00:00-01:00 上传归属当天 |
| 统计 | 聚合前统一按上海日期截断 |

### 11.3 边界用例

1. 上海 2026-12-31 23:59 上传，归属 2026 年。
2. 上海 2027-01-01 00:30 上传，归属 2027 年。
3. 服务器系统时区为 UTC 时，以上结果不变。
4. 浏览器位于其他时区，日历与接口日期仍按上海展示。
5. 周一 00:10 生成上周总结，范围是上周一至上周日（上海）。

## 12. API 设计

### 12.1 通用约定

- 前端 `baseURL="/api"`；Vite/Nginx 将 `/api` 剥离后转发到后端。本文接口表列的是后端路径，前端请求统一加 `/api` 前缀。
- 响应统一 `{code, message, data}`；`code=200` 成功。
- JSON 字段统一 camelCase（Pydantic `alias_generator=to_camel`），与 BigTrans 前端习惯一致；数据库字段保持 snake_case。
- 业务接口统一 `POST` + JSON；文件上传用 `multipart/form-data`；缩略图、原图、健康检查用 `GET`。
- 认证：请求头 `Authorization` 放 JWT 原文，不加 `Bearer`。
- 续签：JWT 剩余 ≤ 1 小时时，响应头 `token` 返回新 token。
- 登录失效：`code=401` 或 `1003`；前端弹窗并跳登录。
- 列表请求：

```json
{
  "page": {"pageNumber": 1, "pageSize": 20},
  "wheres": [
    {"column": "entry_date", "condition": "ge", "v1": "2026-01-01"},
    {"column": "entry_date", "condition": "le", "v1": "2026-12-31"},
    {"column": "note", "condition": "andLike", "v1": "江边"}
  ],
  "orderBys": [{"column": "entry_date", "condition": "desc"}],
  "columns": ["id", "entry_date", "note", "mood"]
}
```

- 列表响应 `data`：`{list: [], totalRow, pageNumber, pageSize}`。
- 所有 ID 字段以字符串返回。

## 13. 认证与加密设计

### 13.1 密码传输

- 服务端生成 RSA-2048 密钥对；私钥仅存服务器环境变量，权限 600。
- 公钥通过 `GET /api/auth/publicKey` 返回，前端缓存。
- 前端使用 `jsencrypt` 以 PKCS#1 v1.5 加密密码，Base64 传输；与 BigTrans `crypto.js` 兼容。
- 登录、注册、修改密码、重置密码的密码字段全部 RSA 加密。
- 后端解密失败、密文为空、解密后长度非法，统一返回参数错误，不透露具体原因。
- 明确：RSA 传输是纵深防御，HTTPS 仍是主保护；禁止只开 HTTP 上线。

### 13.2 密码存储

- 算法：Argon2id，`memory_cost=65536`（64MiB）、`time_cost=3`、`parallelism=2`。
- 参数可配置；登录成功时若参数落后，自动 rehash。
- 密码策略：10-128 位；拒绝常见弱密码（内置 Top 1000）；不强制大小写/符号组合。
- 禁止：明文、MD5、SHA1、SHA-256 单次哈希、三次 Base64。
- 历史兼容：若从 BigTrans 迁移已有 SHA-256 用户，首次登录成功后自动升级为 Argon2id；迁移脚本标记 `password_algo='sha256-legacy'`。

### 13.3 JWT 与会话

- 算法 HS256，密钥 ≥ 256 位，环境变量注入。
- Claims：`sub`（用户 ID）、`userid`、`role`、`ver`（token_version）、`jti`、`iat`、`exp`。
- 默认有效期 8 小时；剩余 ≤ 1 小时时自动续签，响应头 `token` 下发。
- 每次请求校验：
  1. 签名与过期时间；
  2. `dr_user_session.jti` 存在且未撤销；
  3. `com_userlist.user_active='Y'`；
  4. JWT `ver` 等于当前 `token_version`。
- 退出当前设备：撤销对应 `dr_user_session`。
- 退出全部设备/修改密码/禁用账号：`token_version + 1`，并撤销该用户全部会话。
- 会话列表展示：设备、最近活跃、IP 脱敏、创建时间。
- 并发登录：允许，最多保留 10 个活跃会话，超出时撤销最旧会话。
- 图片鉴权：登录成功时同时写入 `dr_token` Cookie（`HttpOnly; Secure; SameSite=Lax; Path=/api/photo`），仅用于浏览器 `<img>` 加载缩略图/原图；API 过滤器优先读 `Authorization`，缺失时读该 Cookie。退出登录时清除 Cookie。这样前端无需用 axios 拉取图片再转 Blob。

### 13.4 登录保护

- 失败计数：Redis key `dr:user:{userid}:failCount`，TTL 15 分钟。
- 阈值：5 次失败锁定 15 分钟；锁定期内直接返回 `1006`。
- IP 限流：登录 10 次/分钟，注册 3 次/小时。
- 登录日志写 `dr_login_log`，记录结果、IP、User-Agent，不记录密码。
- 账号不存在与密码错误统一提示，避免枚举。

### 13.5 其他传输安全

- 全站 HTTPS；HSTS 一年。
- 请求头安全：`X-Content-Type-Options`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、CSP。
- XSS/SQL 过滤：借鉴 BigTrans `RequestAdvice` + `XssAndSqlHttpServletRequestWrapper`，对 JSON body 做关键字过滤，命中返回 `1004`；文件上传跳过。
- 所有 SQL 使用 SQLAlchemy 参数化；禁止拼接。
- JWT 存 localStorage（与 BigTrans 一致），风险由 CSP、Vue 转义、Markdown sanitize 共同控制；不使用 `v-html` 渲染 AI 内容。

- 照片回收站：列表、剩余天数、恢复、彻底删除。
- 导出：JSON / Markdown。
- AI 状态（P2）：开关、模型、成功率。

**系统管理**

- 用户列表：查询表单 + 表格 + 分页 + 启用开关 + 新增/编辑/改密/重置密码/删除，复刻 BigTrans `System/User/index.vue` 模式。
- 用户列表增加"照片库"列：`未开通/开通中/正常/失败`，操作：补开通、重试、重置绑定（不显示 Key）。
- 角色管理：新增/编辑角色；"菜单权限"弹窗用树形勾选配置可见菜单，保存后立即影响该角色用户侧栏；OWNER 固定全部菜单。
- 菜单管理：树形表格展示菜单与分组，支持新增、编辑、删除、排序与启停；路径需对应已有前端路由，分组路径留空。
- 组织管理：树形层级列表，支持新增一级/子组织、编辑、停用、删除；默认组织不可删除。
- 系统设置增加"照片库（Immich）"：展示接入状态、地址说明与未接入提示；管理员按环境变量配置连接。
- 角色/组织/字典：同样采用"查询区 + 表格 + 弹窗"布局。
- 仅 OWNER 可见；`/system/*` 接口二次校验。

### 14.6 请求与状态

- `axios.js` 复刻 BigTrans：
  - `baseURL="/api"`、`timeout=30000`。
  - 请求拦截注入 `Authorization`。
  - 响应拦截读取 `headers.token` 并保存。
  - `code===401 || code===1003` 触发 `handleLoginExpired`，并发去重。
  - `Post/Get` 仅在 `code===200` 时 resolve，否则 `message.error` 并 reject。
- 开发端口：Vite 开发服务器 `5173`，`/api` 代理到 `http://localhost:9111`；生产由 nginx 在 `9110` 统一提供页面与 `/api`。
- `store/auth.js`：token、userInfo localStorage 持久化；`login` 前 RSA 加密；`handleLoginExpired` 弹窗；`logout` 清理。
- `store/dict.js`：启动加载 `/system/dict/list` 全量字典，提供 `options/name/tag` getter。
- 业务状态统一用 Vuex + 页面局部状态，不引入额外状态库。
- 上传：`useMutation` 等价的手写 loading 状态，逐文件进度与失败重试。
- 本地草稿：`localStorage` key `dr:draft:{userId}:{date}`。
- 时间：接口返回的 `yyyy-MM-dd HH:mm:ss` 直接展示，不转 UTC。
- 全局数据版本：`store.state.app.dataVersion = { entries: 0, stats: 0 }`；写操作成功后 `commit('app/bumpDataVersion', ['entries', 'stats'])`。
- 刷新工具 `useAutoRefresh(loader, { interval: 60000, deps })`：负责可见性监听、60 秒轮询、卸载清理与并发去重。

### 14.7 视觉与可访问性

- 沿用 BigTrans 的流光卡片、蓝色主色、深浅主题，但内容区以照片为主，减少装饰。
- 字体：系统字体栈；标题可用衬线体增强记录感。
- 图片：`loading="lazy"`、固定比例占位、`object-fit: cover`。
- 键盘：登录、记录、筛选、热力图均可键盘操作；焦点可见。
- 对比度 ≥ 4.5:1；图标按钮有 `aria-label`。

### 14.8 数据刷新与一致性

| 场景 | 机制 |
|---|---|
| 今天页保存/上传/删除/导入/恢复 | 成功后递增 `entries`、`stats`；当前页局部更新，不整页重载 |
| 时间线进入或 KeepAlive 激活 | `onActivated` 读取 `dataVersion.entries`，与 `renderedVersion` 不同则重拉 |
| 统计页进入或激活 | 同上，比较 `dataVersion.stats` |
| 手动刷新 | `RefreshButton` 调用页面 `load()`，成功后更新"最近更新 HH:mm"并同步版本号 |
| 定时刷新 | 仅页面可见时 60 秒一次，静默模式不显示 loading；请求进行中跳过；页面隐藏暂停 |
| 并发与失败 | 同一接口请求去重；静默刷新失败不弹错误，仅在刷新按钮显示重试状态 |
| 今天页保护 | 编辑态存在 `dirty` 时不接受轮询覆盖；保存后解除 |

实现要点：

- KeepAlive 的页面必须定义 `defineOptions({ name })` 且与路由名一致。
- 版本比较采用"大于则刷新"，刷新成功后写回 `renderedVersion`；避免无限循环。
- 多标签页通过 `storage` 事件同步 `dataVersion`（可选，P1）。

## 15. 安全设计

### 15.1 威胁与对策

| 威胁 | 场景 | 对策 |
|---|---|---|
| 密码泄露 | 抓包、拖库 | RSA 传输 + Argon2id + 禁止日志记录 |
| JWT 被盗 | XSS、设备丢失 | CSP、无 `v-html`、短有效期、会话撤销、token_version |
| 暴力破解 | 撞库、弱密码 | 登录限流、失败锁定、弱密码黑名单 |
| 越权访问 | 改 URL/ID 读他人数据 | 所有查询带 `user_id`；详情用组合条件 |
| 注册滥用 | 公网开放注册 | 默认 CLOSED、邀请码、注册限流 |
| CSRF | 第三方站点发起写请求 | JWT 放请求头而非 Cookie；校验 Origin |
| XSS | AI 输出、用户昵称 | Vue 转义；Markdown sanitize；CSP；后端 XSS 过滤 |
| 恶意上传 | 超大文件、伪造 MIME、压缩炸弹 | 大小限制、MIME 嗅探、Pillow 校验、HEIC 白名单、临时文件隔离 |
| 路径穿越 | 文件名含 `../` | UUID 重命名；扩展名白名单；不用文件名做路径 |
| SSRF | 用户传入 URL | 不提供 URL 参数；上游地址固定配置 |
| SQL 注入 | 搜索/筛选参数 | ORM 参数化；wheres 字段白名单 |
| 公网暴露 | 域名被扫描 | 应用登录 + 可选 Cloudflare Access + 最小端口 + 防火墙默认拒绝 |
| 绕过隧道直连 | 访问 `http://宿主IP:9110` | 端口只绑 `127.0.0.1` 或仅 Docker 内网；云主机安全组/本机防火墙拒绝 9110 |
| 伪造客户端 IP | 直接访问时自填 `X-Forwarded-For` 绕过限流 | 仅信任 cloudflared/nginx，优先读取 `CF-Connecting-IP`；禁止外网直连源站 |
| Immich 管理面暴露 | `/immich/` 反代被扫描/爆破 | 生产不反代 Immich 管理页；缩略图/原图统一由后端代理 |
| Immich API Key 泄露 | 数据库/备份/日志泄露 | 每用户独立 Key；AES-256-GCM + AAD 加密；脱敏返回；禁止日志；最小权限 |
| Immich 管理员 Key 泄露 | 开通权限被滥用 | 仅 OWNER 可配置；加密存储；权限仅 create/update；可快速停用/轮换 |
| 自动开通被滥用 | 恶意注册批量创建 Immich 用户 | 仅 INVITE/OWNER 触发；默认注册 CLOSED；配额 + IP/账号限流 |
| 临时密码泄露 | 开通流程内存/日志泄露 | 仅内存保存；不落库/不返回/不写日志；开通后立即重置失效 |
| 跨账号看照片 | 共用 Immich Key、资产 ID 猜测 | 每用户独立 Immich 用户/Key；Immich 自身权限隔离；代理按当前用户取图 |
| Cloudflare 账号被接管 | 隧道与域名被改 | 强制 2FA、最小权限 Token、隧道凭据文件 600、定期轮换 |
| 备份泄露 | 备份含隐私 | restic 加密；备份盘分离；密钥离线 |

### 15.2 网关与传输

- 全站 HTTPS；HSTS；Cloudflare 侧开启 Always Use HTTPS 与 TLS 1.2+。
- 可选 Cloudflare Access 作为网络层第二道门，不替代应用登录；建议对整个域名启用（含 `/`、`/api`）。
- nginx 安全头：HSTS、nosniff、DENY、no-referrer、CSP。
- 请求体上限：默认 100MB（匹配 Cloudflare 免费/Pro 单请求上限）；局域网直连可调到 200MB。上传 300s，普通 API 30s。
- 登录/注册单独限流；隐藏 `Server` 版本。
- 真实 IP：cloudflared 场景从 `CF-Connecting-IP` 取值；仅当请求来自受信代理网络时才接受转发头，否则使用 socket 地址。
- `ENV=prod` 必须设置，确保 `dr_token` Cookie 带 `Secure`；生产 `CORS_ORIGINS` 只保留自有域名。

### 15.3 多账号与 Immich 边界

- 日记数据按 `user_id` 完全隔离。
- 照片库按应用账号隔离：每个账号绑定独立 Immich 用户与 API Key，搜索、导入、缩略图、原图、上传、清理都使用该账号自己的凭据。
- 后端不提供全局 Immich Key 作为运行时回退；未绑定返回 `1013`，凭据失效返回 `1014`。
- API Key 使用 `CREDENTIAL_ENCRYPTION_KEY` 加密落库，接口只返回后 4 位；日志、审计、错误信息不记录明文。
- 自动开通使用 OWNER 配置的 Immich 管理员 Key；该 Key 只授予 `adminUser.create/update`，单独加密（AAD 不同），不用于日常资产读写。
- 建议使用专用的 Immich 开通管理员账号，不与日常 Immich 登录账号混用；泄露时立即在 Immich 撤销并轮换。
- 临时 Immich 密码只在内存中存在，开通成功后立即重置失效；不保存、不返回、不记录。
- 只有 INVITE/OWNER 创建账号触发自动开通；OPEN 注册默认不触发，并受配额与限流约束。
- 所有者只能重置他人绑定，不能查看他人 Key；Immich 管理员账号与应用账号分离。
- 生产环境不反代 `/immich/`；资产列表/导入走后端 `/api/immich/*`，缩略图走 `/api/immich/thumbnail/{assetId}`，原图走 `/api/photo/original/{id}`。
- 遗留边界：Immich 管理员本身可查看所有 Immich 用户资产；这是 Immich 权限模型，不属于应用能消除的范围。

### 15.4 部署暴露面（Docker + 端口映射 + Cloudflare Tunnel）

**推荐拓扑**

```
公网 → Cloudflare（TLS/WAF/Access）→ cloudflared.exe（宿主机，出站长连接）
     → 127.0.0.1:9110 → web:9110（Docker）
                        ├→ api:9111
                        └→ postgres/redis（不暴露）
```

**已确认方案**

1. `web` 端口绑定 `127.0.0.1:9110:9110`，不监听宿主机公网/局域网；cloudflared 以 Windows 服务运行在宿主机，回源 `http://127.0.0.1:9110`。
2. 宿主机防火墙/云安全组默认拒绝入站，仅保留 SSH（限来源）与必要出站；不配置路由器端口转发。
3. 生产移除 nginx 的 `/immich/` 公网反代；Immich 只在内网可达，缩略图/原图由后端 `/api/immich/thumbnail/{assetId}` 代理。
4. Cloudflare 侧：开启 Access（邮箱/OTP 或 SSO）、WAF 速率限制、Bot Fight、关闭 `/api` 缓存、上传上限与源站超时按实际调整。
5. 真实 IP 与限流：后端只信任隧道/nginx 注入的 `CF-Connecting-IP` 或受信 `X-Forwarded-For`，避免伪造绕过登录限流。
6. `ENV=prod`、强 JWT 密钥、RSA 私钥仅容器内挂载、数据库密码随机、`CREDENTIAL_ENCRYPTION_KEY` 独立离线备份；Cloudflare 账号强制 2FA。
7. 备份加密且与源站分离；删除照片的 30 天回收站同样会被备份，需在隐私说明中注明。

**明确风险**

- Cloudflare Tunnel 在边缘终结 TLS，Cloudflare 可见明文内容；对高度隐私内容，应改用 WireGuard/Tailscale 等私有网络方案，或接受该信任边界。
- Tunnel 不等于"不可发现"：域名会出现在证书透明度日志中，仍会被扫描，必须依赖 Access + 应用认证 + 限流。
- 若宿主机同时把 `9110` 暴露到局域网/公网，则 Cloudflare Access/WAF 全部可被绕过，这是当前方案最需要修正的一点。

## 17. 可靠性与降级

### 17.1 依赖降级矩阵

| 故障 | 影响 | 降级行为 |
|---|---|---|
| Immich 不可用 | 无法上传、缩略图失败、导入失败 | 已有记录可读；上传按钮禁用并提示；缩略图用缓存或占位 |
| Ollama 不可用（P2） | 描述/总结失败 | 记录与上传正常；任务保持 `pending`；前端提示稍后重试 |
| PostgreSQL 不可用 | 全站不可用 | `/ready` 返回 503；nginx 维护页 |
| Redis 不可用 | 登录失败计数失效 | 记录与登录继续；退化为内存计数并告警 |
| cloudflared 断开 | 外网不可访问 | 局域网仍可用；Uptime Kuma 告警 |
| 磁盘满 | 上传失败、DB 只读风险 | 监控阈值 80%；上传前检查空间；告警 |
| JWT 密钥泄露 | 可伪造 token | 轮换密钥、提升 token_version、撤销全部会话 |

### 17.2 备份与恢复

- 每日 03:00（上海）：
  - `pg_dump -Fc` 导出 `diary` 与 `immich` 两个库。
  - restic 备份：数据库 dump、Immich 上传目录、Compose 与 `.env`（加密）。
  - 目标：第二块硬盘 + 异地对象存储（可选）。
- 保留：7 日、4 周、12 月。
- 恢复演练：每季度一次，恢复数据库与 10 张照片，启动只读实例抽查。
- RPO 24h，RTO 4h。

### 17.3 升级与回滚

- Immich 与自有服务镜像固定 tag/digest，不使用 `latest` 自动升级。
- 升级流程：备份 → 拉取新镜像 → `docker compose up -d` → 冒烟 → 观察 24h。
- 回滚：切回旧 tag + 恢复备份（若迁移不兼容）。
- 数据库迁移只向前；紧急回滚使用备份。

### 19.2 网络与端口

- 前端 nginx 监听 **9110**，只绑定 `127.0.0.1`；后端 FastAPI 监听 **9111**，仅 Docker 内网可达（调试时临时映射）。
- 公网 HTTPS 由 Cloudflare 终结，宿主机 `cloudflared.exe` 出站长连接回源到 `http://127.0.0.1:9110`；不开放路由器端口映射。
- PostgreSQL、Redis、Immich、Ollama 只在 Docker 内网可达。
- 防火墙默认拒绝入站，仅保留 SSH（限 IP）与 cloudflared 出站；如需局域网直连，只对可信网段放行 9110，并明确这会绕过 Cloudflare Access/WAF。
- `docker-compose.yml` 的 `web.ports` 必须写为 `"127.0.0.1:${WEB_PORT:-9110}:9110"`；Windows 防火墙额外拒绝 9110 入站。

### 19.3 nginx 关键配置

```nginx
server {
    listen 9110;
    server_name diary.example.com;
    client_max_body_size 100m;  # 与 Cloudflare 单请求上限一致

    location /api/ {
        proxy_pass http://diary-api:9111/;
        proxy_read_timeout 300s;
        proxy_set_header X-Request-ID $request_id;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # 生产不提供公网 Immich 反代；缩略图/原图统一走 /api/photo/*
    # 如确需内网调试，单独在 127.0.0.1 的 server 块开放，并加 IP 白名单

    location / {
        root /usr/share/nginx/html;
        try_files $uri /index.html;
    }

    location /api/photo/ {
        proxy_pass http://diary-api:9111/photo/;
        proxy_cache photo_cache;
        proxy_cache_valid 200 7d;
    }

    location = /api/auth/login {
        limit_req zone=login burst=5 nodelay;
        proxy_pass http://diary-api:9111/auth/login;
    }
}
```

仓库内的部署文件：

| 文件 | 作用 |

| `frontend/Dockerfile` | 阶段一 `node:18.20-alpine` 构建，阶段二 `nginx:1.27-alpine` 托管，监听 9110 |

| `scripts/update.sh` | 拉代码、拉基础镜像、重建、重启、清理悬空镜像；版本号参数与 `build.sh` 一致 |

构建与更新：

```bash
cp .env.example .env
# 编辑 .env：POSTGRES_PASSWORD、JWT_SECRET、RSA_PRIVATE_KEY、RSA_PUBLIC_KEY
# IMMICH_URL、CREDENTIAL_ENCRYPTION_KEY（每个用户再在账户设置绑定自己的 Immich API Key）

# 首次构建并启动，等待健康检查（版本自动为 0.1.1）
sh scripts/build.sh --check

# 指定版本号构建
sh scripts/build.sh 1.2.3 --check
sh scripts/build.sh --version 1.2.3 --check

# 日常换包更新（不指定版本时自动递增补丁号）
sh scripts/update.sh
sh scripts/update.sh --version 1.2.4
```

说明：

- 版本号以仓库根目录 `VERSION` 为准；不传版本号时按当前版本计算 `X.Y.(Z+1)` 并写回 `VERSION`。
- 构建时 `APP_VERSION` 同时写入 `.env`，镜像打标签 `dailyrecord-api:<版本>`、`dailyrecord-web:<版本>`；`docker compose up` 可直接复用该标签。
- 后端通过 `GET /health` 返回 `version`，前端账户设置展示同一版本号，便于确认实际部署版本。

- 后端容器通过 `alembic upgrade head` 自动迁移（存在 `alembic.ini` 时），随后启动 Uvicorn。
- 前端镜像构建完成后，nginx 通过官方镜像的 `envsubst` 注入 `${API_UPSTREAM}`；不再需要 `${IMMICH_UPSTREAM}`。
- 只有 `web` 映射宿主端口 `9110`，且绑定 `127.0.0.1`；`api` 仅暴露在 Docker 内网 `9111`。
- Immich 通过后端 `IMMICH_URL` 访问；若 Immich 在宿主机，使用 `http://host.docker.internal:2283`；若同 Docker 网络，使用 `http://immich-server:2283`。前端不再依赖 `IMMICH_UPSTREAM`。
- 镜像构建要求 `backend/app/main.py` 与 `frontend/package.json` 已存在；这两个文件在 M1 落地后即可直接构建。
- 回滚：切回上一个 Git tag，再执行一次 `sh scripts/build.sh`；数据库迁移不兼容时先恢复备份。

### 19.7 回收站清理任务

- 命令：`docker compose exec -T api python -m app.cli purge-photos`；支持 `--dry-run` 输出待清理清单。
- 调度（二选一）：
  - 宿主机 cron：`30 3 * * * cd /opt/dailyrecord && docker compose exec -T api python -m app.cli purge-photos >> /var/log/dailyrecord/purge.log 2>&1`
  - Compose 内 `diary-worker` 服务：同镜像、`restart: "no"`，由 cron/systemd timer 触发。
- 任务要求：幂等、可重入、单次 ≤ 500 条、失败重试 3 次；结果写 `dr_job_run`，每条清理写 `dr_change_log`。
- 监控：连续 2 天失败或待清理数超过 1000 时告警（Uptime Kuma / 邮件）。
- 备份策略：回收站照片在删除前仍会被日常备份包含；到期清理后，下一轮备份自然不再包含。

### 19.8 自动开通重试任务

- 调度：`diary-worker` 每 5 分钟扫描 `provision_status in ('pending','failed') AND provision_attempts < 3`。
- 单次上限 10 个，串行执行，避免同时打满 Immich。
- 重试仍沿用 FR-13：管理员重置临时密码 → 登录 → 建 Key → 重置密码 → 加密入库。
- 超过 3 次标记 `failed`，等待 OWNER 手动补开通；不自动删除已创建的 Immich 用户。
- 结果写 `dr_job_run`（`job_name='immich_provision'`）与审计日志，不记录任何密钥材料。

## 23. 验收标准（Definition of Done）

MVP 完成需同时满足：

1. 所有 MVP 功能需求通过第 20.2 节用例。

7. 年视图、统计、筛选数字一致。
8. 备份任务连续运行 7 天，完成一次恢复演练。
9. 性能达到 16.3 节目标（允许老机器单项放宽 20%，需记录）。
10. 无 P0/P1 缺陷；P2 缺陷有清单与计划。
11. 运维手册包含部署、升级、回滚、备份、恢复、故障排查。
12. 代码通过 lint、类型检查、单元与集成测试。
13. 负责人可在手机与桌面完成一次"注册-记录-回看"完整流程。
14. AI 关闭时，除描述与总结外的全部功能可用；AI 入口有明确说明。
15. 保存记录后，时间线/统计自动同步；手动刷新与可见时轮询符合 14.8。
16. 记录、照片、标签的修改均可在界面查看时间、操作人与增减内容；日志不可修改。

### D. BigTrans 复用要点（给 AI 编码助手）

1. 系统表直接使用 `zymonitor-backend/sql/init.sql`，只执行第 10.2 节的扩展语句。
2. 登录流程照 `UserServiceImpl.login`：RSA 私钥解密 → 校验密码 → 生成 token → 更新登录时间。密码校验改为 Argon2id。
3. JWT 过滤器照 `JwtTokenFilter`：`Authorization` 原文、HS256、响应头 `token` 续签；额外校验 `dr_user_session`。
4. 响应照 `Result` / `ResultCode`；业务错误返回 HTTP 200 + 业务 code。
5. 前端 axios 照 `zymonitor-web/src/api/axios.js`；`code===200` 才 resolve，401/1003 统一处理。
6. 登录页照 `views/Login/index.vue`；布局照 `BasicLayout.vue`；主题变量照 `theme.less`；卡片照 `modules.css`。
7. 系统用户页照 `views/System/User/index.vue` 的查询区 + 表格 + 分页 + 弹窗模式。
8. 不照搬：三次 Base64、SHA-256 密码、ctos3 注解、多租户组织逻辑、Flink/Kafka 模块。

### E. 开发约定

1. 先读本文件与设计概要，任何实现不得偏离第 5、10、11、12、13 节契约。
2. 数据库变更必须写 Alembic 迁移，禁止 `create_all` 上生产。
3. 所有业务查询必须带 `user_id` 条件；禁止只按日期或 ID 查询后在前端过滤。
4. 密码、JWT、RSA、Cookie 必须使用本文件指定方案，禁止自创加密。
5. 时间统一走 `services/timeutil.py`，禁止业务代码直接 `datetime.now()`。
6. Immich 与 Ollama 调用只放在 `services/`，统一异常转换为业务错误码。
7. 所有 API 必须有 Pydantic 请求/响应模型与统一 `Result` 包装。
8. 后端 ruff + black + mypy（可选）；前端 ESLint + Prettier + Less 嵌套；禁止 `!important`。
9. 每个功能附带单元或集成测试；提交前本地跑通。
10. 不引入未列出的基础设施依赖（消息队列、Elasticsearch 等）。
11. 不记录用户正文、描述、文件名、密码、JWT 到日志。
12. AI 代码必须受 `AI_ENABLED` 与 `DAILYRECORD_AI_ENABLED` 控制，未开启时不得启动 Worker 或阻塞主流程。
13. 完成一个模块即更新文档，保持文档与代码一致。
